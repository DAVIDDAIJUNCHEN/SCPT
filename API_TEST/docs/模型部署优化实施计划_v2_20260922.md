> 生成日期：2026-09-22
> 范围：AlloMax 平台（admin org=100002）模型部署优化 + 星语网关同步
> 依据：全部基于实测数据（KV 池、commands 基线、并发核算）+ 官方参数出处核查

## 总原则

1. **每实例只重建一次 pod**：ctx 提升、并发保护、显存调优打包进同一次 GUI 改动——每次 PUT 冷启动 5~15 min，分开改等于把停机窗口放大 3~4 倍
2. **保护优先于性能**：先给「裸奔」（`max_running=None`）的实例上保险，再提 1M
3. **实验先于上线**：qwen3.8 的 YaRN 属未验证项，先在 node006 `docker run` 验证，通过才上 AlloMax
4. **所有参数必须有官方出处**（ModelScope 模型页 / SGLang 官方文档），不瞎想——此前出过「SGLang 参数给了 vLLM」的事故
5. 🆕 **输入输出双约束**：目标为 **1M 输入 + 384K 输出**，两者共享同一个 ctx 预算，且必须满足 `maxInputTokens + maxOutputTokens ≤ ctx`

## 〇-A、🆕 输入/输出双约束设计（2026-09-22 新增）

> **状态：⏸️ 暂缓（2026-09-22 12:30 用户决策）**
> **当前决策：维持现状 —— 专注 1M 输入，384K 输出需求暂不推进，长输出保护策略亦暂不做。**
> 本节核算结论保留，作为将来重启该需求时的依据，无需重算。

### 目标（暂缓）

| 维度 | 目标值 | 出处 |
|---|---|---|
| 输入（prompt） | **1M**（1,048,576） | DeepSeek-V4.1-Flash 官方 README：`context_window = 1M tokens` |
| 输出（completion） | ~~384K（393,216）~~ ⏸️ | 业务目标（官方 README 为 `max_tokens ≥ 256K` 下界，384K 在其之上、能力范围内，但**非官方推荐值**） |

### 🔴 关键约束：两者不可同时吃满

```
1,048,576 (1M 输入) + 393,216 (384K 输出) = 1,441,792  >  ctx 1,048,576
```

服务端 ctx 是**输入+输出的总量池**，单请求无法同时达到 1M 输入和 384K 输出。若将来要启用 384K 输出，需在客户端配置上做取舍：

| 方案 | maxInputTokens | maxOutputTokens | 总和 | 权衡 |
|---|---|---|---|---|
| A. 输入优先 | 655,360 | 393,216 | 1,048,576 | ✅ 可跑满 384K 输出；输入上限降到 640K |
| B. 均衡 | 913,408 | 131,072 | 1,044,480 | 输入 896K / 输出 128K，覆盖绝大多数场景 |
| C. 输出优先 | 1,048,576 | 32,768 | 1,081,344 | ❌ 超限 |
| **D. 当前采用** | **1,048,576** | **32,768** | **1,081,344** | ⚠️ 轻微超限但实测可用（服务端 `max_req_input_len=1048570`）；**已实测 357K 输入通过** |

### 🆕 384K 输出的真实代价（暂缓，保留核算）

以实测 KV 池 28,661,248 tokens 核算：

| 场景 | 单请求总 token | 并发路数 |
|---|---|---|
| 纯 384K 输出 | 393,216 | **72 路** |
| 128K 入 + 384K 出 | 524,288 | 54 路 |
| 1M 输入满载 | 1,048,576 | 27 路 |

**并发路数不是瓶颈，驻留时长才是**——KV 池按 token 总量计，长输出请求会长时间占住池：

| 解码速度 | 单个 384K 输出请求占用 KV 池时长 |
|---|---|
| 30 tok/s | **218 分钟** |
| 50 tok/s | **131 分钟** |
| 80 tok/s | 82 分钟 |

**结论（供将来参考）**：一个 384K 长输出请求会独占约 1.4~3.6 小时的 KV 资源。48 路并发若同时发起长输出，需 18,874,368 tokens（池的 66%）——届时必须在网关层加「长输出专属限流 + 超时」，而非简单调大 `max_running_requests`。

## 五、超载行为说明（为什么不会崩）

| 阶段 | 触发条件 | 用户感受 | 服务状态 |
|---|---|---|---|
| 变慢 | 并发 > GPU 算力上限 | 首 token 慢、逐字变卡 | ✅ 正常排队调度 |
| 排队 | KV 池被长请求占满 | 请求挂起数秒~分钟 | ✅ `max_queued_requests` 兜底 |
| 拒绝 | 队列也满了 | **429/503 明确报错**，可重试 | ✅ 保护生效 |
| 真崩 ⚠ | **无并发上限**时超量涌入 | 大面积 502，恢复 6~15 min | ❌ OOM / 调度死锁 |

当前隐患：glm-5.3-flash 和 GLM-5.3 满血 `max_running_requests=None`（裸奔），是崩险最高的两个——T2/T3 优先补齐。
