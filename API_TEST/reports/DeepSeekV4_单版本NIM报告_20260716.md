## 3. 详细测试数据

### 3.1 吞吐率与首字符响应时间 (TTFT)

| Prompt 类型 | 长度 (tokens) | 平均 TTFT (ms) | P99 TTFT (ms) | 平均吞吐 (tok/s) | 输出长度 (tokens) |
|------------|--------------|---------------|--------------|-----------------|------------------|
| 短 (short) | ~10 | 154 | 195 | 120.0 | ~93 |
| 中 (medium) | ~16 | 168 | 254 | 119.0 | ~254 |
| 长 (long) | ~32 | 169 | 206 | 133.0 | ~1,771 |

**分析**：

- TTFT 随 prompt 长度变化趋势：几乎持平（154→168→169ms），说明 prefill 开销极低，三种 prompt 长度差异不足以触发明显退化。这与直连 NIM 去除代理延迟后的表现一致。
- 短 prompt 下 TTFT 是否满足交互式需求 (<200ms)：是，P99 也仅 195ms。
- 吞吐率与输出长度的关系：正相关。短 prompt 约 120 tok/s，长 prompt 约 133 tok/s。原因：输出越长，prefill 时间占比越低，生成阶段的 GPU 利用率更充分。
- 对比代理轮：代理轮 Medium P99 TTFT 高达 1300ms（冷启动），直连轮降至 254ms。消除代理跳转后延迟波动显著收窄。

### 3.2 并发性能测试

| 并发数 | 有效请求数 | 系统吞吐 (tok/s) | 平均 TTFT (ms) | 墙钟耗时 (s) | 失败原因 |
|--------|-----------|-----------------|---------------|-------------|---------|
| 1 | 1/1 | 124 | 156 | 1.8 | 无 |
| 2 | 2/2 | 199 | 161 | 2.5 | 无 |
| 4 | 4/4 | 358 | 275 | 2.7 | 无 |
| 8 | 8/8 | 620 | 276 | 3.2 | 无 |
| 16 | 16/16 | 1,100 | 271 | 3.4 | 无 |
| 32 | 32/32 | 1,713 | 409 | 4.5 | 无 |
| 64 | 64/64 | 2,381 | 548 | 6.5 | 无 |

**关键发现**：

1. **64 并发零失败**，与代理轮（8 并发即报 `peer closed connection`）形成鲜明对比。代理层是瓶颈，非模型本身。

2. **墙钟耗时几乎不增长**：1→64 并发，墙钟仅从 1.8s 增至 6.5s（3.6×），而请求量增加了 64×。这是 continuous batching 的典型表现——GPU 在并发生成多个序列，wall time 增长远低于线性。

3. **TTFT 保持可控**：32 并发时 TTFT 升至 409ms，64 并发 548ms。对于非实时场景（如批量文档处理）完全可接受；对实时对话场景建议控制在 16 并发以内（TTFT 271ms）。

4. **系统吞吐近线性扩展**：1→64 并发，吞吐从 124→2,381 tok/s（19.2×）。说明单请求远未吃满 GPU，并发越多 GPU 利用率越饱和。

**并发瓶颈判断**：64 并发下 TTFT 仍仅 548ms 且无失败，推测还可进一步压测 128/256 并发。当前瓶颈不在模型，可能在 GPU 计算单元或显存带宽。建议补测上限。

**对比代理轮**：

| 并发 | 代理轮吞吐 | 直连轮吞吐 | 代理轮 TTFT | 直连轮 TTFT |
|------|----------|----------|-----------|-----------|
| 8 | 29 tok/s | 620 tok/s | 808ms | 276ms |
| 64 | 41 tok/s | 2,381 tok/s | 739ms | 548ms |

### 3.4 显存消耗分析

> 本轮未安装 pynvml，显存数据待补。以下为理论估算。

#### 3.4.1 理论估算

**模型权重**：
- DeepSeek V4 Flash 采用 MoE 架构，总参数量未公开，激活参数推测约 20B
- BF16 精度下：激活参数 20B × 2 bytes = 40 GB；若总参数 70B 则需 140 GB（多卡）
- 结合 64 并发 zero fail 的表现，推测为多卡部署，单卡显存 ≥ 80 GB

**KV Cache 每 token 消耗**（经验公式估算）：
- 公式：2 × n_layers × n_kv_heads × d_head × dtype_size
- 假设 n_layers=40, n_kv_heads=40, d_head=128, BF16
- 计算：2 × 40 × 40 × 128 × 2 = 819,200 字节 ≈ 0.78 MB/token

**KV Cache 总消耗**（按 64 并发、每请求 16 tokens 输入 + 250 tokens 输出估算）：
- 单请求 KV：~(16+250) × 0.78 = 207 MB
- 64 并发 KV：207 × 64 ≈ 13 GB
- 该估算偏低，实际还需计入 NIM 内部 overhead，推测 KV Cache 总消耗在 15-25 GB

### 4.3 部署建议

1. **绕过代理层**：本轮数据明确证明 AI 中台代理是性能瓶颈。生产环境必须直连 NIM，或确保代理无连接池限制和超时掐断。
2. **并发配额**：此部署 64 并发无压力，建议生产环境开放 ≥ 32。
3. **长上下文策略**：对 > 32K 的请求做客户端流式提示，告知 prefill 预计耗时，避免用户困惑。
4. **补显存监控**：`pip install nvidia-ml-py` 后重跑测试四，记录空载→满并发→OOM 的显存曲线。

## 6. 结论

DeepSeek V4 Flash 直连 NIM 部署下表现如下：

**核心优势**：
1. TTFT 极快（154ms），交互体验流畅
2. 并发扩展性优秀，64 并发 zero fail，系统吞吐 2,381 tok/s
3. 128K 上下文窗口完整可用，全部测试通过
4. continuous batching 效率高，墙钟耗时随并发增长缓慢

**主要不足**：
1. 长上下文 cold prefill 偏慢（65K→16.7s），会影响全量分析场景的首字体验
2. 显存数据缺失，无法评估资源效率上限
3. 并发上限未探明，64 并发后性能走向未知

**生产环境部署意见**：
- 此部署可用于实时对话（32 并发以内）、RAG 检索（4K-32K）、批量文档处理（64 并发高吞吐）三类场景
- 生产上线前必须补测并发上限和显存数据
- AI 中台代理层对吞吐有致命影响，已在本轮对比中证实，必须直连
