#### 3.4.2 理论估算

**模型权重**：
- 参数量：`假设 70B (MoE 激活约 20B)`
- 精度：`BF16 (2 字节/参数)`
- 权重显存：`70B × 2 = 140 GB` (需多卡) 或 `20B × 2 = 40 GB` (单卡)

**KV Cache 每 token 消耗**：
- 公式：`2 × n_layers × n_kv_heads × d_head × dtype_size`
- 假设：`n_layers=40, n_kv_heads=40, d_head=128, dtype=BF16`
- 计算：`2 × 40 × 40 × 128 × 2 = 819,200 字节 ≈ 0.78 MB/token`

**KV Cache 总消耗**：
- 单请求：`seq_len × 0.78 MB`
- 并发场景：`batch_size × seq_len × 0.78 MB`

#### 3.4.3 显存瓶颈分析

- **主要瓶颈**：`模型权重 / KV Cache / 激活值`
- **OOM 触发点**：`并发数 > N 或 上下文长度 > M`
- **优化建议**：`调整 max_model_len / 降低 batch_size / 使用 PagedAttention`

### 4.2 优化建议

1. **部署配置优化**
   - 调整 `max_num_seqs` 和 `max_model_len` 平衡并发与显存
   - 考虑使用 `FP8` 量化进一步降低显存
   - 启用 `PagedAttention` 提高 KV Cache 利用率

2. **硬件选型建议**
   - 单卡场景：`推荐至少 80GB 显存 GPU`
   - 多卡场景：`推荐使用 NVLink 互联`
   - 内存带宽：`关注 HBM 带宽，建议 > 2 TB/s`

3. **应用层适配**
   - 短 prompt 场景：`可启用 speculative decoding`
   - 长上下文场景：`建议分块处理，减少单次请求长度`
   - 高并发场景：`设置合理的请求超时和排队机制`

## 5. 测试限制与后续工作

### 5.1 测试限制
- 未测试 `speculative decoding` 等高级特性
- 未覆盖 `function calling` / `tool use` 场景
- 网络延迟未计入（本地测试）
- 未测试长时间稳定性（7x24 小时）

### 5.2 后续测试建议
1. **稳定性测试**：7x24 小时持续请求，观察显存泄漏/性能下降
2. **混合负载测试**：短/长 prompt 混合，模拟真实场景
3. **多卡扩展性**：测试 2/4/8 卡下的线性加速比
4. **量化对比**：BF16 vs FP8 vs INT8 的精度/速度权衡

## 6. 结论

DeepSeek V4 Flash 在测试环境中表现出：

**优势**：
1. `TTFT 优秀，适合交互式应用`
2. `吞吐率较高，单卡可达 XX tok/s`
3. `上下文窗口实测达 N tokens，满足多数场景`
4. `并发能力良好，支持 X 个并发用户`

**待改进**：
1. `长上下文下 TTFT 退化明显`
2. `高并发时易触发 OOM`
3. `显存消耗较大，需高端 GPU`

**推荐应用场景**：
- `实时对话应用 (并发数 < N)`
- `中等长度文档处理 (< M tokens)`
- `对响应速度要求高的交互场景`

**不推荐场景**：
- `超长文档一次性处理 (> L tokens)`
- `超高并发 (> C 用户) 无负载均衡`
- `显存受限的边端设备`
