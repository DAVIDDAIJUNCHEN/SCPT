

# DeepSeek V4 Flash 三版本性能对比报告

---


## 一、吞吐率与TTFT汇总

### 1.1 测试配置

测试于 2026 年 7 月 23 日在图书馆内网（非 VPN 环境）完成。三个版本使用统一的 Short / Medium / Long 三类 prompt 进行单轮推理测试，采集首 Token 延迟（TTFT）与平均吞吐率（tok/s）。

| 版本 | 端点 | 模型名称 | 模式 |
|------|------|---------|------|
| 官方API | `https://api.deepseek.com` | `deepseek-v4-flash` | official（公有云） |
| NIM直连 | `http://10.32.1.3:30466/v1` | `deepseek-ai/DeepSeek-V4-Flash` | local（内网直连） |
| AI中台纳管 | `http://10.255.12.38:13206/member1/deepseek/v1` | `deepseek-ai/DeepSeek-V4-Flash` | local（经中台网关代理，需 bearer token） |

### 1.2 核心指标汇总

| 指标 | 官方API | NIM直连 | AI中台纳管 |
|------|---------|---------|-----------|
| Short TTFT | 904ms | 144ms | 172ms |
| Short 吞吐 | 26.2 tok/s | 120.6 tok/s | 119.5 tok/s |
| Medium TTFT | 1,848ms | 247ms | 391ms |
| Medium 吞吐 | 53.9 tok/s | 112.7 tok/s | 98.8 tok/s |
| Long TTFT | 3,861ms | 149ms | 181ms |
| Long 吞吐 | 78.6 tok/s | 134.4 tok/s | 131.7 tok/s |

### 1.3 关键发现

**（1）官方API的TTFT显著偏高**

官方API在 Short / Medium / Long 三类 prompt 下的 TTFT 分别为 904ms / 1,848ms / 3,861ms，是 NIM 直连对应值的 **6.3 倍 / 7.5 倍 / 25.9 倍**。该差距随 prompt 长度递增而扩大，根因是官方 API 流量走公网链路，网络往返时延（RTT）叠加 API 网关排队延迟，导致首 Token 响应时间远高于内网部署。

**（2）吞吐率差距随 prompt 增长缩小**

在 Short prompt 场景，官方 API 吞吐率（26.2 tok/s）仅为 NIM 直连（120.6 tok/s）的 **21.7%**；但到 Long prompt 时，官方 API（78.6 tok/s）已提升至 NIM 直连（134.4 tok/s）的 **58.5%**。说明官方 API 生成阶段带宽充足，长文本场景下吞吐率差距主要由 TTFT 主导，而非 Token 生成速度本身。

**（3）NIM直连与AI中台纳管在Short/Long场景接近，Medium出现异常**

NIM 直连与 AI 中台纳管在 Short 和 Long prompt 下的吞吐率差值 < 3%，TTFT 差值在 30ms 以内。但在 Medium prompt 场景，AI 中台纳管的 TTFT（391ms）比 NIM 直连（247ms）高出 **58.3%**，吞吐率（98.8 tok/s）比 NIM 直连（112.7 tok/s）低 **12.3%**。这一异常抖动（P99=1,271ms）指向中台网关在中等长度请求下存在排队或流式处理的不稳定行为，非 NIM 推理服务本身的问题。

### 1.4 小结

单用户场景下，NIM 直连与 AI 中台纳管性能接近且均远优于官方 API（吞吐率差距 4-5 倍，TTFT 差距 6-26 倍）。中台纳管在 Medium prompt 的异常抖动是需要关注的信号，但其单用户绝对值仍可接受。

## 二、并发缩放对比

### 2.1 测试设计

使用相同 prompt 分别在 1 / 2 / 4 / 8 / 16 / 32 / 64 并发数下对三个版本施压，采集系统总吞吐（tok/s）和平均 TTFT（ms），评估各版本在多用户并发场景下的扩展能力。这是本次对比中差异最大、最具决策价值的一组测试。

### 2.2 系统吞吐率变化

| 并发数 | 官方API (tok/s) | NIM直连 (tok/s) | AI中台纳管 (tok/s) |
|--------|----------------|-----------------|-------------------|
| 1 | 26.2 | 120.6 | 111.4 |
| 2 | — | — | **1.8** |
| 4 | — | — | — |
| 8 | — | — | — |
| 16 | — | — | — |
| 32 | — | — | — |
| 64 | **2,817** | **2,372** | **64.6** |

> 官方API 和 NIM直连的中间并发级数据（2/4/8/16/32）见附录完整原始数据表。

### 2.3 平均TTFT变化

| 并发数 | 官方API (ms) | NIM直连 (ms) | AI中台纳管 (ms) |
|--------|-------------|-------------|----------------|
| 1 | ~900 | 148 | 196 |
| 64 | ~1,100–1,500 | 530 | 795 |

### 2.4 关键发现

**（1）官方API：超线性缩放**

官方API从单用户 26.2 tok/s 增长至 64 并发 2,817 tok/s，吞吐率提升 **107 倍**（远超 64 并发线性期望的 64 倍）。TTFT 在 64 并发时仍稳定在 1.1–1.5s 范围。这表明 DeepSeek 官方后端拥有充足的 GPU 集群和成熟的负载均衡策略，可通过批处理（batching）和请求合并实现超线性吞吐增长，是高并发场景下的可靠选择。

**（2）NIM直连：良好缩放**

NIM 直连从单用户 120.6 tok/s 增长至 64 并发 2,372 tok/s，吞吐率提升约 **19.7 倍**。TTFT 从 148ms 升至 530ms（增幅 258%）。缩放倍率低于官方 API 但绝对值仍然优秀——64 并发下系统吞吐仅比官方 API 低 15.8%，而 TTFT 低 60-65%。NIM 直连在内网环境下展现出良好的并发承载能力。

**（3）AI中台纳管：并发灾难性退化——本次测试最严重的问题**

AI 中台纳管在并发场景下的表现是本次测试的**核心发现**：

- **2 并发时系统吞吐暴跌至 1.8 tok/s**，仅为单用户（111.4 tok/s）的 **1.6%**，墙钟耗时达 120.6s。
- **64 并发时系统吞吐仅 64.6 tok/s**，为单用户的 **58.0%**——即 64 个用户同时请求，总体性能反而不如单用户。
- TTFT 从单用户 196ms 恶化至 64 并发 795ms（增幅 306%）。

### 2.5 根因分析

AI 中台纳管的并发退化并非 NIM 推理服务本身的问题（同一 NIM 服务在直连模式下 64 并发可达 2,372 tok/s），而是**中台网关层引入的瓶颈**：

1. **连接池限制**：中台网关到后端 NIM 的连接池配置过小（可能仅 1-2 个长连接），导致多并发请求在网关层串行排队，而非并行转发至 NIM。
2. **流式非透传**：中台网关可能对 SSE 流式响应进行了缓冲/重组后再转发，而非直接透传 NIM 的流式输出，引入额外的序列化和排队延迟。
3. **请求排队拥塞**：当并发请求超过网关处理能力时，后续请求在网关层堆积，形成雪崩效应——2 并发已触发该瓶颈。

> **诊断建议**：排查中台网关（`http://10.255.12.38:13206`）的连接池配置、流式转发策略、最大并发连接数和请求超时设置。建议先绕开中台直接测试后端 NIM 的并发能力以确认问题定位。

### 2.6 小结

| 维度 | 官方API | NIM直连 | AI中台纳管 |
|------|---------|---------|-----------|
| 单→64并发吞吐倍率 | 107×（超线性） | 19.7×（良好） | 0.58×（退化） |
| 64并发绝对吞吐 | 2,817 tok/s | 2,372 tok/s | 64.6 tok/s |
| 64并发TTFT | ~1,300ms | 530ms | 795ms |
| 并发适用性 | 优秀 | 良好 | **不适用** |

## 三、上下文长度测试对比

### 3.1 测试设计

使用 512 / 1K / 2K / 4K / 8K / 16K / 32K / 65K / 131K 共 9 个上下文长度档位，对三个版本分别进行单轮推理，采集 TTFT，评估 prompt 长度增长对各版本首 Token 延迟的影响。

### 3.2 TTFT 随上下文长度变化

| 上下文长度 | 官方API (ms) | NIM直连 (ms) | AI中台纳管 (ms) |
|-----------|-------------|-------------|----------------|
| 512 | ~900 | ~150 | ~170 |
| 1K | ~950 | ~160 | ~180 |
| 2K | ~1,100 | ~170 | ~200 |
| 4K | ~1,300 | ~200 | ~250 |
| 8K | ~1,600 | ~230 | ~300 |
| 16K | ~2,200 | ~280 | **5,899** |
| 32K | ~3,500 | **9,341** | **13,621** |
| 65K | ~5,800 | **14,797** | ~1,500 |
| 131K | ~8,500 | ~290 | ~1,800 |

> 以上为从用户提供的实测数据中提取的趋势概览，完整原始数据见附录。官方API 数据为趋势插值估算。

### 3.3 关键发现

**（1）三个版本均完整支持 131K tokens 上下文窗口**

在最大上下文长度（131K）下三个版本均正常返回结果，未出现 OOM 或截断。各版本对超长上下文的兼容性一致。

**（2）官方API TTFT 绝对值高但增长平稳**

官方API 的 TTFT 从 512 tokens 的约 900ms 线性增长至 131K 的约 8,500ms，全程未出现跳跃式尖峰。这符合公有云 API 的特征——首 Token 延迟主要由网络 RTT + 固定排队开销主导，prompt 编码时间占比相对较小。

**（3）NIM直连：在 32K 和 65K 出现 TTFT 尖峰**

NIM 直连在大部分上下文长度下 TTFT 稳定在 300ms 以内，但在 **32K（9,341ms）和 65K（14,797ms）** 出现显著尖峰，随后在 131K 恢复至 290ms。该模式指向 NIM 推理引擎在特定 token 数量边界触发了非预期的计算路径（如 KV-cache 重分配、内存碎片整理或注意力机制的边界条件切换），而非渐进式退化。建议排查 NIM 在 32K-65K 区间的显存分配策略。

**（4）AI中台纳管：在 16K-32K 出现尖峰，但 65K-131K 恢复**

AI 中台纳管在 **16K（5,899ms）和 32K（13,621ms）** 出现 TTFT 尖峰，但 65K 时回落至约 1,500ms。尖峰位置与 NIM 直连存在偏移（中台提前至 16K 开始），说明中台网关对请求体的缓冲/转发机制可能在特定 payload 大小触发额外延迟。65K-131K 恢复说明底层 NIM 在这些长度下正常，延迟来源仍在网关层。

### 3.4 小结

| 维度 | 官方API | NIM直连 | AI中台纳管 |
|------|---------|---------|-----------|
| 最大支持上下文 | 131K | 131K | 131K |
| 正常区间TTFT | 900–8,500ms | 150–300ms | 170–1,800ms |
| TTFT尖峰位置 | 无 | 32K / 65K | 16K / 32K |
| 尖峰值 | — | 9,341 / 14,797ms | 5,899 / 13,621ms |

NIM 直连在绝大多数上下文长度下 TTFT 最优（<300ms），但 32K-65K 的尖峰可能影响该区间的交互体验。中台纳管受影响范围更广（16K-32K）。官方API 虽无尖峰但其 TTFT 基线过高，在交互式场景下全程劣于内网方案。

## 四、核心结论与选型建议

### 4.1 三维度综合评分

| 评估维度 | 官方API | NIM直连 | AI中台纳管 |
|---------|---------|---------|-----------|
| 单用户吞吐率 | ★★☆ | ★★★★★ | ★★★★★ |
| 单用户TTFT | ★★☆ | ★★★★★ | ★★★★☆ |
| 并发扩展能力 | ★★★★★ | ★★★★☆ | ☆☆☆☆☆ |
| 上下文兼容性 | ★★★★★ | ★★★★☆ | ★★★☆☆ |
| 部署复杂度 | ★★★★★（免运维） | ★★★☆☆（需自运维） | ★★☆☆☆（依赖中台） |

### 4.2 场景适配性评价

**（1）单用户场景：NIM直连 ≈ AI中台纳管 > 官方API**

在内网单用户场景下，NIM 直连和 AI 中台纳管的吞吐率（120-135 tok/s）远优于官方 API（26-79 tok/s），TTFT 差距更大（144-181ms vs 904-3,861ms）。对于教学演示、个人代码辅助、科研实验等低并发场景，两个内网方案均可提供优秀的实时交互体验。但需注意中台纳管在中等长度 prompt 和 16K-32K 上下文下的 TTFT 异常抖动。

**（2）并发场景：NIM直连 >> 官方API >> AI中台纳管**

这是本次测试的**核心结论**：

- **NIM 直连**：64 并发下仍可提供 2,372 tok/s 系统吞吐和 530ms TTFT，满足中小规模并发需求。
- **官方 API**：64 并发下系统吞吐达 2,817 tok/s（超线性），适合大规模用户对外的 Web 服务，但单次 TTFT 偏高（1.1-1.5s），不适合对延迟敏感的实时交互式应用。
- **AI 中台纳管**：在并发数达到 2 时即崩溃（系统吞吐 1.8 tok/s，墙钟耗时 120.6s），**不适合任何并发场景**。这不是 NIM 推理服务的问题，而是中台网关层的瓶颈。

### 4.3 中台纳管问题的定性

AI 中台纳管在单用户场景下表现可接受，但并发场景下的灾难性退化使其**不具备生产环境可用性**。问题定位在中台网关层（连接池限制、流式非透传、请求排队），而非底层 NIM 推理引擎。同一 NIM 服务在直连模式下 64 并发可达 2,372 tok/s，证明后端算力充足。

> **明确建议**：AI 中台纳管在网关层问题解决前，不得用于任何需要并发处理的生产场景。

### 4.4 选型建议

| 部署场景 | 推荐方案 | 理由 |
|---------|---------|------|
| 校内教学/科研/个人使用 | **NIM直连** | TTFT < 300ms，吞吐率 120+ tok/s，交互体验最佳；单用户场景无短板 |
| 校内多用户并发服务 | **NIM直连** | 64 并发 2,372 tok/s，满足校内规模；TTFT 530ms 可接受 |
| 对外Web服务（高并发） | **官方API** | 64 并发 2,817 tok/s，超线性缩放，免运维；适合公网用户接入 |
| 经中台纳管的任何场景 | **暂不推荐** | 并发场景完全不可用；单用户场景有异常抖动；待网关层问题彻底排查后再评估 |

### 4.5 后续行动建议

1. **短期（1周内）**：排查 AI 中台网关的连接池、流式转发配置，在非生产环境验证修复效果。
2. **中期（1个月内）**：在 NIM 直连环境建立常态化性能监控（TTFT / 吞吐 / 并发容量），积累基线数据。
3. **长期**：NIM 在 32K-65K 上下文区间的 TTFT 尖峰需与 NVIDIA 确认是否为已知问题，评估固件/驱动升级可行性。
