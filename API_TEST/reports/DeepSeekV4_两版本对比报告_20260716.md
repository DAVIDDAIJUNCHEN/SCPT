**结论**：单请求场景下，AI 中台代理引入的延迟约 10-16ms（不到 10%），吞吐几乎一致。单请求用户基本无感知。

## 4. 上下文长度对比（测试三）

### 4.1 成功率

| 上下文长度 | NIM 原生 | AI 中台 |
|-----------|---------|---------|
| 512 | 成功 | 异常（TTFT=0, 输出=0） |
| 1K-131K | 全部成功 | 全部成功 |

> 512 处 AI 中台返回 0 token，疑似中台对极小输出做了截断或被 prefix caching 干扰了解析。

### 4.2 65K 长上下文 prefill 对比

| 指标 | NIM 原生 | AI 中台 | 差异 |
|------|---------|---------|------|
| 65K TTFT | 16,692ms | 35,554ms | +113% |

这是除并发外最显著的差距。65K tokens 的 prefill 在中台路径下慢了整整一倍。推测中台对长请求体做了完整缓冲后再转发（而非流式透传），导致首 token 需要等待整个请求体在中台侧完成接收和校验。

## 5. 综合对比结论

### 5.1 一页总览

| 维度 | NIM 原生 | AI 中台 | 中台损耗 | 严重程度 |
|------|---------|---------|---------|---------|
| 单请求 TTFT | 154-169ms | 168-184ms | +10-15ms | 低，可忽略 |
| 单请求吞吐 | 120-133 tok/s | 117-134 tok/s | ±3% | 低，可忽略 |
| 并发吞吐（4+） | 358→2,381 tok/s | 14→464 tok/s | 最高 -98% | 致命 |
| 并发成功率 | 100% | 50%-100%（波动） | 最多 50% 失败 | 致命 |
| 并发 TTFT 稳定性 | 平滑增长 | 剧烈震荡 | P99 波动 +46-100% | 高 |
| 长上下文 prefill | 16.7s (65K) | 35.6s (65K) | +113% | 高 |
| 上下文窗口 | 128K 全通过 | 128K 全通过 | 无影响 | — |

### 5.2 中台瓶颈根因推断

```
客户端 ──→ AI 中台 ──→ NIM
              │
              ├─ 连接池上限 ≈ 8（推测）
              ├─ 超时策略：长请求/无活动流即掐断
              ├─ 请求体缓冲：大请求体完整接收后才转发
              └─ 无流式透传或透传有节流
```

| 现象 | 对应的中台配置问题 |
|------|------------------|
| 2 并发即崩溃 | 连接池最小连接数可能为 1，第 2 个请求需等待新建连接 |
| 8 并发是唯一正常点 | 连接池 max 约 8，8 以内恰好不排队 |
| 16+ 吞吐剧烈波动 | 排队 + 超时掐断 + 重试风暴 |
| 65K prefill 慢 2 倍 | 请求体缓冲策略（64K×4char ≈ 256KB 在中台侧完整接收后才转发） |
| peer closed connection | 中台侧 idle timeout 或 max request duration |

### 5.3 适用场景建议

| 场景 | NIM 原生 | AI 中台 |
|------|---------|---------|
| 单用户问答/对话 | 适用 | 适用（差异 <10%） |
| RAG 检索增强 | 适用 | 适用（prefill 增加可接受） |
| 多用户并发（>2） | 适用 | 不适用 |
| 批量文档处理 | 适用 | 不适用（吞吐崩塌） |
| 长文档全量分析（>32K） | 勉强可用 | 不适用（prefill 翻倍） |
| 生产环境 API 服务 | 推荐 | 需改造中台配置 |

## 6. 给中台的改造建议

按优先级排序：

1. **连接池扩容**：将 NIM 上游连接池从当前约 8 提升至 ≥ 64，支持多用户并发
2. **流式透传**：请求体和响应体均做流式透传（chunked transfer），不要在中台侧完整缓冲后再转发
3. **超时对齐**：中台侧 idle timeout 对齐 NIM 生成耗时（长上下文请求可能需要 30-60s 无 token 输出），当前明显偏短
4. **连接复用**：对同一 NIM 后端启用 HTTP/2 多路复用或连接池预热，消除首请求建连延迟
5. **透传 /models 端点**：让客户端可以看到可用模型列表，便于调试和健康检查
