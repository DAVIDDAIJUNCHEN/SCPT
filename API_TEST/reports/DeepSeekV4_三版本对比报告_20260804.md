本次测试环境由 0726 的图书馆内网（非 VPN）切换为 0804 的家庭 WiFi + 学校 VPN 环境（测试时间 2026-08-04 21:23~21:33）。三版本 1M 上下文均测试成功（base_text 已修复），相比 0726 仅覆盖到 267K 是重大进步。官方 API 模型名已从 `deepseek-v4-flash` 更名为 `deepseek-chat`。

| 版本 | 指标 | 0726（图书馆） | 0804（家+VPN） | 变化 | 评价 |
|------|------|---------------|----------------|------|------|
| 官方API | Short TTFT | 904ms | 609ms | ↓33% | 大幅改善 |
| 官方API | Medium TTFT | 1,848ms | 579ms | ↓69% | 质变 |
| 官方API | Long TTFT | 3,861ms | 676ms | ↓82% | 史诗级优化 |
| 官方API | 64并发吞吐 | 2,817 tok/s | 4,406 tok/s | ↑56% | 大幅提升 |
| 官方API | 单用户Long吞吐 | 78.6 tok/s | 101.1 tok/s | ↑29% | 持续改善 |
| 官方API | 最大上下文 | 131K | 1M | ↑663% | 扩容至百万 |
| 官方API | 1M上下文TTFT | N/A | 28,899ms | — | 新增能力 |
| NIM直连 | Short TTFT | 144ms | 157ms | +9% | VPN影响轻微 |
| NIM直连 | Medium TTFT | 247ms | 157ms | ↓36% | 改善 |
| NIM直连 | 32K上下文TTFT | 9,341ms | 229ms | ↓98% | 尖峰彻底修复 |
| NIM直连 | 65K上下文TTFT | 14,797ms | 350ms | ↓98% | 尖峰彻底修复 |
| NIM直连 | 131K上下文TTFT | 357ms | 1,728ms | ↑384% | VPN+大上下文影响显著 |

| AI中台 | 131K上下文TTFT | 500ms | 4,236ms | ↑747% | VPN下显著退化 |
| AI中台 | 1M上下文TTFT | N/A | 4,149ms | — | VPN下优于NIM直连 |
| AI中台 | 1K上下文异常 | — | 1,472ms | — | VPN抖动 |

**核心变化总结**：

- **官方API 全面加速**：TTFT 从秒级进入亚秒级（Long 场景从 3,861ms 降至 676ms），64 并发吞吐从 2,817 升至 4,406 tok/s，上下文窗口从 131K 扩容至 1M。
- **NIM 直连 32K-65K 尖峰彻底消失**：0726 的 9,341ms / 14,797ms 异常尖峰已修复，但 VPN 下大上下文（>131K）TTFT 显著膨胀，1M 达 100 秒。
- **AI 中台并发灾难完全修复**：2 并发吞吐从 1.8 tok/s 跃升至 193.0 tok/s（106 倍），64 并发从 64.6 升至 2,351 tok/s（36 倍），已恢复至与 NIM 直连同级水平。
- **VPN 对大上下文影响显著**：NIM 直连 131K TTFT 从 357ms 升至 1,728ms（↑384%），1M 达 100,072ms。AI 中台 1M 仅 4,149ms，推测中台网关有连接复用或缓存机制。

## 二、0804（新版）完整性能对比

### 2.1 测试配置

测试于 2026 年 8 月 4 日在家中 WiFi + 学校 VPN 环境下完成。三个版本使用统一的 Short / Medium / Long 三类 prompt 进行单轮推理测试，采集首 Token 延迟（TTFT）与平均吞吐率（tok/s）。

| 版本 | 端点 | 模型名称 | 模式 |
|------|------|---------|------|
| 官方API | `https://api.deepseek.com` | `deepseek-chat` | official（公有云） |
| NIM直连 | `http://10.32.1.3:30466/v1` | `deepseek-ai/DeepSeek-V4-Flash` | local（内网VPN直连） |
| AI中台纳管 | `http://10.255.12.38:13206/member1/deepseek/v1` | `deepseek-ai/DeepSeek-V4-Flash` | local（经中台网关代理，需 bearer token） |

### 2.2 吞吐率与TTFT汇总

| 指标 | 官方API | NIM直连 | AI中台纳管 |
|------|---------|---------|-----------|
| Short TTFT | 609ms | 157ms | 207ms |
| Short P99 | 823ms | 172ms | 214ms |
| Short 吞吐 | 37.1 tok/s | 116.1 tok/s | 114.7 tok/s |
| Medium TTFT | 579ms | 157ms | 203ms |
| Medium P99 | 777ms | 175ms | 209ms |
| Medium 吞吐 | 88.0 tok/s | 121.0 tok/s | 116.7 tok/s |
| Long TTFT | 676ms | 157ms | 213ms |
| Long P99 | 953ms | 160ms | 222ms |
| Long 吞吐 | 101.1 tok/s | 133.3 tok/s | 133.9 tok/s |

### 2.3 关键发现

**（1）官方API TTFT 全面进入亚秒级**

相比 0726，官方 API 在 Short / Medium / Long 三类 prompt 下的 TTFT 分别降至 609ms / 579ms / 676ms。Long prompt 场景从 3,861ms 降至 676ms（↓82%），意味着即使是长 prompt 也能在 1 秒内获得首 Token 响应。该改善推测来自官方后端推理加速和 API 网关优化。

**（2）官方API 吞吐率随 prompt 增长明显提升**

Short 场景输出较短（~33 tokens），生成阶段占比低，吞吐率仅 37.1 tok/s。到 Long 场景时吞吐率升至 101.1 tok/s，说明官方 API 生成阶段的 Token 输出速度充足。实际体验中长文生成流畅度已接近内网方案。

**（3）NIM直连与AI中台纳管在 Short/Medium/Long 上高度接近**

两个内网方案在全部三个 prompt 类型下 TTFT 差值 < 60ms，吞吐率差值 < 5 tok/s。0726 报告中 AI 中台 Medium TTFT 异常（391ms，P99=1,271ms）已消失，本轮 P99 仅 209ms，说明中台网关在单用户场景下的稳定性显著改善。

**（4）VPN 对小上下文影响轻微**

NIM 直连 Short TTFT 从 0726 的 144ms 升至 157ms（+13ms），AI 中台从 172ms 升至 207ms（+35ms）。VPN 引入的额外延迟在 15-35ms 量级，对 Short 场景几乎无感知影响。

### 3.3 关键发现

**（1）AI中台纳管并发能力完全恢复——本轮最重大变化**

0726 报告中 AI 中台纳管在 2 并发时吞吐暴跌至 1.8 tok/s，64 并发仅 64.6 tok/s，被判定为"并发灾难性退化"。本轮测试中：

- 2 并发吞吐 193.0 tok/s（0726 为 1.8 tok/s，↑106 倍）
- 64 并发吞吐 2,350.6 tok/s（0726 为 64.6 tok/s，↑36 倍）
- 64 并发吞吐已反超 NIM 直连（2,350.6 vs 2,327.6 tok/s）

说明中台网关的连接池/流式转发瓶颈已得到修复，AI 中台纳管现已具备生产环境并发能力。

**（2）官方API 超线性缩放持续增强**

官方 API 从单用户 84.8 tok/s 增长至 64 并发 4,405.6 tok/s，吞吐率提升约 **52 倍**（远超 64 并发线性期望）。相比 0726 的 2,817 tok/s 进一步提升 56%。64 并发下 TTFT 仅 602ms，完全可满足实时交互需求。

**（3）三个版本 64 并发吞吐排名：官方API > AI中台 ≈ NIM直连**

64 并发下三个版本吞吐分别为 4,406 / 2,351 / 2,328 tok/s。官方 API 拥有超线性缩放优势，两个内网方案性能接近。在 VPN 环境下 NIM 直连与 AI 中台的差异已基本抹平。

**（4）VPN 对并发 TTFT 的影响**

NIM 直连 64 并发 TTFT 531ms（0726 为 530ms，持平），AI 中台 820ms（0726 为 795ms，+25ms）。VPN 引入的额外延迟在并发场景下仍可控。

### 3.4 小结

| 维度 | 官方API | NIM直连 | AI中台纳管 |
|------|---------|---------|-----------|
| 单→64并发吞吐倍率 | 52×（超线性） | 20.3×（良好） | 20.3×（良好） |
| 64并发绝对吞吐 | 4,406 tok/s | 2,328 tok/s | 2,351 tok/s |
| 64并发TTFT | 602ms | 531ms | 820ms |
| 并发适用性 | 优秀 | 良好 | **良好（已修复）** |

## 四、上下文长度测试对比

### 4.1 TTFT 随上下文长度变化

| 上下文长度 | 官方API (ms) | NIM直连 (ms) | AI中台纳管 (ms) |
|-----------|-------------|-------------|----------------|
| 512 | 818 | 159 | 232 |
| 1K | 1,224 | 156 | **1,472** |
| 2K | 920 | 149 | 216 |
| 4K | 747 | 164 | 641 |
| 8K | 1,337 | 170 | 1,739 |
| 16K | 985 | 186 | 1,229 |
| 32K | 1,197 | 229 | 1,223 |
| 65K | 1,342 | 350 | 1,918 |
| 131K | 1,401 | **1,728** | **4,236** |
| 1M | **28,899** | **100,072** | **4,149** |

### 4.2 关键发现

**（1）三版本 1M 上下文全部成功**

本轮测试中三个版本在 1M tokens 上下文下均正常返回结果，未出现 OOM 或截断。相比 0726 仅覆盖到 131K（且 base_text 问题导致实际仅到 267K），上下文的全面测试是本次的重要进展。

**（2）NIM直连 32K-65K 尖峰彻底消失**

0726 报告中 NIM 直连在 32K（9,341ms）和 65K（14,797ms）的 TTFT 尖峰已不复存在。本轮对应值分别为 229ms 和 350ms，说明 NIM 推理引擎在该区间的问题已修复。

**（3）VPN 对大上下文（>32K）影响显著**

- NIM 直连 131K TTFT 从 0726 的 357ms 升至 1,728ms（↑384%），1M 达 100,072ms（约 1 分 40 秒），基本不可用于交互式场景。
- AI 中台 131K TTFT 从 0726 的约 500ms 升至 4,236ms（↑747%），但 1M 仅 4,149ms——远优于 NIM 直连的 100,072ms。

**（4）AI中台 1M 表现异常优异——推测连接复用**

AI 中台在 1M 上下文下 TTFT 仅 4,149ms，而 NIM 直连为 100,072ms（差距 24 倍）。两者后端为同一 NIM 推理服务，差异只能来源于中台网关层。推测中台网关采用了 HTTP 长连接复用或请求缓冲优化，避免了每次请求重新建立 TCP+TLS 连接的开销，在 VPN 高延迟链路下收益显著。

**（5）AI中台 1K 上下文出现异常抖动**

AI 中台在 1K 上下文时 TTFT 为 1,472ms，明显高于相邻档位（512: 232ms, 2K: 216ms）。该孤立异常点可能是 VPN 链路的瞬时抖动（丢包重传），非中台系统性缺陷。类似抖动在 4K（641ms）和 8K（1,739ms）也有轻微体现。

**（6）官方API 上下文 TTFT 保持平稳**

官方 API 从 512 到 131K 全程 TTFT 在 747-1,401ms 范围内波动，无尖峰。1M 时升至 28,899ms（约 29 秒），在大上下文场景下仍可接受——考虑到 1M tokens 的 prompt 编码计算量，该延迟在预期范围内。

### 4.3 小结

| 维度 | 官方API | NIM直连 | AI中台纳管 |
|------|---------|---------|-----------|
| 最大支持上下文 | 1M | 1M | 1M |
| 正常区间TTFT（≤131K） | 747–1,401ms | 149–1,728ms | 216–4,236ms |
| 1M TTFT | 28,899ms | 100,072ms | 4,149ms |
| TTFT尖峰位置 | 无 | 131K起（VPN影响） | 1K（偶发抖动） |
| VPN对大上下文影响 | N/A（公网） | 严重（1M=100s） | 轻微（疑似连接复用） |

## 五、核心结论与选型建议

### 5.1 三维度综合评分

| 评估维度 | 官方API | NIM直连 | AI中台纳管 |
|---------|---------|---------|-----------|
| 单用户吞吐率 | ★★★☆ | ★★★★★ | ★★★★★ |
| 单用户TTFT | ★★★☆ | ★★★★★ | ★★★★☆ |
| 并发扩展能力 | ★★★★★ | ★★★★☆ | ★★★★☆ |
| 上下文兼容性 | ★★★★★ | ★★★★☆ | ★★★★☆ |
| VPN大上下文适配 | ★★★☆☆ | ★☆☆☆☆ | ★★★★☆ |
| 部署复杂度 | ★★★★★（免运维） | ★★★☆☆（需自运维） | ★★☆☆☆（依赖中台） |

### 5.2 环境因素影响总结

| 上下文范围 | VPN 影响（NIM直连） | VPN 影响（AI中台） |
|-----------|-------------------|-------------------|
| ≤32K | 轻微（+10~20ms） | 轻微（+30~50ms） |
| 32K~131K | 显著（TTFT 放大 4-5×） | 中等（TTFT 放大 2-8×） |
| 1M | 严重（100 秒，不可用） | 较优（4.1 秒，可用） |

VPN 对小上下文（≤32K）的影响几乎可忽略，但从 131K 开始 NIM 直连 TTFT 急剧膨胀。AI 中台得益于网关层的连接复用机制，在大上下文下表现远超 NIM 直连。

### 5.3 场景推荐矩阵

| 部署场景 | 网络环境 | 推荐方案 | 理由 |
|---------|---------|---------|------|
| 校内教学/科研/个人使用 | 图书馆内网 | **NIM直连** | TTFT < 160ms，吞吐 120+ tok/s，全纬度最优 |
| 校内教学/科研/个人使用 | 家里VPN | **NIM直连** | 小上下文性能不受影响；大上下文建议限制 ≤32K |
| 校内多用户并发服务 | 图书馆内网 | **NIM直连 或 AI中台** | 两者 64 并发均达 2,300+ tok/s，从运维便利性选中台 |
| 校内多用户并发服务 | 家里VPN | **AI中台** | 并发能力与 NIM 持平，大上下文更优（1M 仅 4.1s） |
| 大上下文应用（>131K） | 图书馆内网 | **NIM直连 或 AI中台** | 两者均可用，1M TTFT 待内网测试验证 |
| 大上下文应用（>131K） | 家里VPN | **AI中台** | 1M TTFT 4,149ms vs NIM 直连 100,072ms，差距 24 倍 |
| 对外Web服务（高并发） | 公网 | **官方API** | 64 并发 4,406 tok/s，超线性缩放，免运维 |
| 对延迟敏感的实时交互 | 任意 | **NIM直连（内网）或官方API（公网）** | NIM 小上下文 TTFT < 160ms；官方 API 已进入亚秒级 |

### 5.4 0804 相比 0726 的重大变化总结

1. **官方API TTFT 质变**：从秒级（904-3,861ms）全面进入亚秒级（579-676ms），可用性大幅提升。
2. **AI中台并发灾难完全修复**：2 并发吞吐从 1.8→193.0 tok/s（↑106 倍），64 并发从 64.6→2,351 tok/s（↑36 倍），已具备生产环境并发能力。
3. **NIM 32K-65K 尖峰消失**：0726 报告的 9,341ms / 14,797ms 异常尖峰已修复，内网全范围 TTFT 稳定。
4. **上下文窗口从 131K 扩展至 1M**：三版本全部支持，配合 base_text 修复，超长上下文测试完整。
5. **VPN 环境引入新变量**：大上下文（>131K）场景下 NIM 直连严重退化（1M=100s），AI 中台凭借连接复用优势（1M=4.1s），场景选型需区分网络环境。

### 5.5 后续行动建议

1. **短期（1周内）**：在图书馆内网环境补充 1M 上下文测试（NIM 直连和 AI 中台），获取无 VPN 干扰下的基线数据，验证 1M 场景真实的延迟表现。
2. **中期（1个月内）**：针对 VPN 大上下文退化问题，与网络团队确认 VPN 链路的 MTU、TCP 窗口和丢包率，评估优化空间。
3. **长期**：在 AI 中台纳管建立常态化性能监控（TTFT / 吞吐 / 并发容量），持续跟踪网关层优化效果。
